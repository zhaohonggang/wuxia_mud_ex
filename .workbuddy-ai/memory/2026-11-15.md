## dev_start.bat 重新编译修改过 .ex 的原因（2026-11-15，当前会话）

- **现象**：用户在 Windows 主机上修改 `.ex` 文件（如 `vendor/kalevala/lib/kalevala/character/foreman.ex`），Ctrl+C 停止容器后再运行 `dev_start.bat`，可以看到容器内重新编译了该文件，修改生效。
- **根因链条**：
  1. **Bind mount 源码**：`docker-compose.dev.yml` 第 34 行 `- .:/app` 将 Windows 主机源码目录挂载到容器内 `/app`，Windows 上的文件修改会立即同步到容器。
  2. **Named volume 保留编译产物**：`app_build:/app/_build`（第 38 行）是 Docker named volume，容器重启时保留已编译 BEAM，不会自动丢失。
  3. **`code_reloader: false`**：`config/dev.exs` 第 21 行，Phoenix Endpoint 关闭代码热重载，运行中的 BEAM 不会自动重新加载修改后的代码，必须容器重启。
  4. **容器重启时 Mix 增量编译**：`dev_start.bat` 第 51 行 `%COMPOSE% up app` 启动容器，容器入口点 `mix phx.server`（`docker-compose.dev.yml` 第 118 行）。Mix 在启动时比较源文件 mtime 与已编译 BEAM 的 mtime，由于源码通过 bind mount 从 Windows 映射，修改后的文件在容器内的时间戳会更新，Mix 检测到源文件比 BEAM 新，触发增量编译该文件。
- **结论**：`dev_start.bat` 本身不显式运行 `mix compile`，而是通过 `docker compose up app` 启动容器，由 `mix phx.server` 触发 Mix 的增量编译检查。任何在 Windows 上修改的 `.ex` 文件都会在下次容器启动时被重新编译并加载。
- **验证**：用户实际操作 Ctrl+C 后 `dev_start.bat`，看到 `foreman.ex` 被重新编译，`jing` 从 15/120 开始自动恢复，修复生效。
