# 慢编译排查：commands.ex 单文件 28s

## 结论（已定位，用户决定不修）
`lib/kantele/character/commands.ex` 单文件冷编译 **28s**，属**正常现象**，非卡死。

根因：该文件用 `Kalevala.Character.Command.Router` DSL 注册了 **452 个 `parse`**（212 个 `module` 块），
每个 `parse` 展开成一个 `defparsecp`，即 452 个 NimbleParsec 解析器编进同一模块。
NimbleParsec **0.6.0** 的编译期代码生成很慢。

## 实测数据（Docker, MIX_ENV=test）
| 项目 | 耗时 |
|------|------|
| `elixirc` 空启动基线 | 687ms |
| 100 个普通 def | 840ms（约 153ms 净） |
| 100 个 `defparsecp`（简单文法） | 2685ms（约 2000ms 净 ≈ 20ms/个） |
| 真实 `commands.ex`（452 个 parse，含 choice/concat/optional） | **27976ms ≈ 28s** |

单文件 28s ≈ 60ms/解析器；`Enum.find_value` 按源码顺序匹配，最大块是 `MoveCommand`（70 个方向 parse）。

## 尝试过但已回滚
升级 `nimble_parsec` 0.6.0 → 1.4.2（root `override: true` + vendor/kalevala `~> 1.0`）：
- 能编过（`defparsecp` 在 1.x 仍存在），但**用户明确拒绝升级**——"不要升级了，编译时间长点不是问题"。
- 已 `git checkout --` 还原 `mix.exs` / `mix.lock` / `vendor/kalevala/mix.exs`，
  容器内 `mix deps.get` + 重编回 0.6.0，并 `docker compose -f docker-compose.dev.yml restart app`。

## 硬性约定
**不要升级 nimble_parsec。** 编译慢是可接受代价。

## 若将来要提速（未实施，仅备忘）
1. 拆分 `commands.ex` 成多个文件/路由模块 —— Elixir 按**文件**并行编译，可显著缩短墙钟时间；但 `@parse_functions` 顺序语义要保住。
2. 折叠重复 parse：`MoveCommand` 的 70 个方向 parse 可合并成 1 个 `choice([...])`（需让 handler 从 `params["command"]` 取方向）。
3. 注意 `parse("answer", :run, fn ... end)` 这类用 `optional(empty() |> spaces() |> text(:rest))` 的写法本身不慢。
