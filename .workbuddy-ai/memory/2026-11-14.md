## 修复：衡阳猎人收捕兽夹门控（marks/hunter 缺失）

**根因**：`data/world/hengyang.ucl` 的 `characters "hunter"` 的 `accept` 规则写成
`kind = "item_id" id = "bushou jia" accept = true msg = ["这是什么东西，我不需要！"...]`，
与 LPC `hunter.c` 的 `accept_object` 不一致：LPC 收到捕兽夹会 `set_temp("marks/hunter", 1)`，
但端口旧规则既没置位 marks/hunter，还弹出错误台词，导致 `ask hunter about hunting` /
`learn hunting 猎人` 永远被 `Kantele.NPC.Hunter.hunter_mark?` 挡在「你我素无往来」。

**修复（沿用 reborn/suoyangdan accept 模式）**：
- UCL：`accept` 改为 `{ kind = "hunter" id = "bushou jia" msg = [...] }`。
- 新建 `lib/kantele/world/hunter_accept.ex`：`handle/5` 在猎人进程内向玩家发
  `hunter/give-trap` 事件并渲染 LPC 台词，不进猎人背包（类比 reborn/suoyangdan）。
- `lib/kantele/character/events/give_event.ex`：
  - `handle_accept_give` 增 `{:hunter}` → `HunterAccept.handle`；
  - `match_accept_rule` reduce 增 `:hunter -> {:hunter}` 与 `{:hunter} -> acc`；
  - `rule_hit` 增 `%{kind: "hunter"}`（`rule.id == item.id` 才命中）；
  - 新增玩家侧 `hunter_give_trap/2`：移除捕兽夹实例、`PlayerMeta.put_mark("hunter", 1)`
    + `put_temp("marks/hunter", 1)`、`Records.save`，台词提示。
- `lib/kantele/character/events.ex`：路由 `event("hunter/give-trap", :hunter_give_trap)`。
- 测试：`test/kantele/character/events/give_event_hunter_test.exs`（5 例全绿）。

**验证**：`mix test give_event_hunter_test.exs` 5/5 通过；关联 `give_command_test.exs` /
`give_event_wuxiuwen_test.exs` / `hunter_test.exs` 共 25 例 0 失败。
注：`Records.save` 在测试里报 `null gender` 等为合成角色缺字段，属测试环境噪声，
与 wuxiuwen 既有测试同现象，不影响断言。

## 二次修复：加载器白名单丢弃特殊 accept kind（这才是「没反应」真因）

**现象**：用户实测 `give 猎人 捕兽夹` 仍「没反应」。追查发现上一轮的 UCL/Accept 改法本身对，
但 `lib/kantele/world/loader.ex:917` 的 `parse_accept_rules` 白名单只有
`["money","item_id","item_name","any"]`，**会把 `forge/wuxiuwen/reborn/suoyangdan/hunter`
全部丢成 nil** → 猎人（及地藏王/莫邪/武修文/阎罗）的 `meta.accept == nil` →
`generic_accept?` 为假 → give 落到 `handle_normal_give`（NPC 只收物品、不触发任何 accept 逻辑）。
上一轮单元测之所以绿，是因为测试直接把 accept 规则塞进 `NonPlayerMeta`，绕过了加载器。

**修复**：
- `loader.ex` 白名单扩为含 `forge/wuxiuwen/reborn/suoyangdan/hunter`（纯增量，不破坏已有规则）。
- 测试补 `Loader.parse_character` 真实加载路径用例：确认 `hunter` 等被保留、未知 kind 仍丢弃。
- 现 `give_event_hunter_test.exs` 共 8 例 0 失败。

**连带影响（重要）**：此白名单缺陷同样让 `reborn/forge/wuxiuwen/suoyangdan` 的 accept 规则
在**线上一直没加载**（之前只靠测试里直接注入规则才「通过」）。本次一并修复后，
给地藏王精元丹、给莫邪材料、给武修文还工具、给阎罗药引 这些流程线上才真正可用。
若用户此前反馈过这些流程「没反应」，根因同此。

**上线注意**：加载器改动需重启/重载世界，NPC 进程重新从 UCL 生成才会带 `accept`，
运行中的旧实例仍是 nil。

## 三次修复：accept 规则 id 与实际物品 id 不匹配（这才是「重启后仍没反应」的真因）

**现象**：上一轮（加载器白名单）修完后重启，`give 猎人 捕兽夹` 仍「没反应」。

**根因**：`lib/kantele/world/loader.ex:1415` `item.id = "#{zone.id}:#{key}"` —— 物品真实 id
带区前缀+点号键（捕兽夹 = `clone_lib:items.bushoujia` 之类），而 UCL accept 规则写的是
`id = "bushou jia"`（LPC 原始 id，无区前缀）。`rule_hit(%{kind:"hunter"})` 的
`rule.id == item.id` 永远不等 → `:miss` → 规则不命中 → 落到 `give/result(ok:false)`（玩家侧
"对方不肯收下"）/ 或静默。单元测此前用合成物品 id `"bushou jia"` 自匹配，故一直绿、没暴露。

**修复**：改用 **name 匹配**，避免依赖易错的 id 字符串。
- `hengyang.ucl` 猎人 accept：`id = "bushou jia"` → `name = "捕兽夹"`。
- `give_event.ex` `rule_hit(%{kind:"hunter"})`：先试 `rule.id == item.id`，再试
  `Kantele.World.Item.matches?(item, rule.name)`（与 `item_name` 规则同款匹配逻辑）。
- 测试改走 name 路径（`accept: [%{kind:"hunter", name:"捕兽夹"}]`），8 例全绿。

**经验教训（重要）**：本项目物品 id 形如 `zone:items.xxx`，**绝不能用原始 LPC id 字符串**
（如 `bushou jia` / `wu zhi rong`）去对 `item.id`。accept / quest / drop 等凡要按物品比对的地方，
优先按 **name / aliases** 匹配；若必须用 id，先用 `Items.get` 确认真实 `item.id` 再写。
（连带：beijing 的 `wu zhi rong`、quanzhen 的 `gui jia`/`fu ling`、jingzhou 的 `lv juhua`/`ye juhua`
等 `item_id` 类 accept 规则大概率也有同样 id 错位，属潜在未触发 bug，但用户未报，暂不扩面修。）

**上线注意（再次）**：本次又改了 `give_event.ex` + `hengyang.ucl`，**需再重启一次**才会生效；
上一次重启只吃到了加载器白名单那半截修复。

## 四次修复（最终根因）：NPC 事件路由缺 `characters/give` → give 整体在线上「没反应」

**现象**：用户实测 `give 猎人 捕兽夹`「没有任何反应，连日志都没有」，并质疑「游戏里到底有没有
give 这个命令」。前三轮（UCL 规则 / 加载器白名单 / id→name）改动都对，但线上依旧无反应。

**排查**：先确认 `give`/`给` 命令确实已注册（`lib/kantele/character/commands.ex:179` 两个 parse
都挂 `GiveCommand.run`，`router_aliases_test.exs:116-123` 路由测试通过）。命令存在，故问题在运行时流。
关键线索：`GiveCommand.do_give` 发出 `room/give` 后 `assign(:prompt, false)`，赠者回执完全依赖
NPC 进程回发的 `give/result` / `hunter/give-trap`；只要 NPC 侧不处理 `characters/give`，赠者就收不到
任何回执 → 体感「完全没反应，连日志都没有」。

**真因**：事件路由分两套 —— 玩家用 `Kantele.Character.Events`，NPC 用 `Kantele.Character.NonPlayerEvents`
（见 `spawn_controller.ex`）。`characters/give` → `GiveEvent.receive` 只注册在 **玩家** 路由里
（`events.ex:84`）。**NPC 路由里根本没有 `characters/give`**，所以房间把 `characters/give` 转发给猎人
进程后被静默丢弃。前三轮单测之所以全绿，是因为它们直接调 `GiveEvent.receive(conn, event)`，绕过了
真正的 NPC 事件路由，没暴露这一层缺失。

**修复**：在 `NonPlayerEvents`（`events.ex` 内 `scope(Kantele.Character)` 块）补挂收受端：
```elixir
module(GiveEvent) do
  event("characters/give", :receive)
end
```
只挂收受端 `:receive`；回执类（give/result、hunter/give-trap、reborn/suoyangdan 等）都在玩家侧
`Kantele.Character.Events`，NPC 侧不需要。这样所有 NPC 都能接收 give（此前给任意 NPC 都「没反应」，
属通用性 bug，本次一并修好）。

**回归测试**：给 `give_event_hunter_test.exs` 增 2 例，直接走 `NonPlayerEvents.call(conn, event)`：
- 猎人收捕兽夹 → 经路由命中 GiveEvent.receive → HunterAccept 发 `hunter/give-trap`；
- NPC 无 accept 规则时也仍能收到事件（走 `handle_normal_give` 回 `give/result(ok:true)`），
  验证不再静默丢弃。现该文件 10 例、关联 3 文件合计 42 例 0 失败。

**结论**：给猎人捕兽夹的完整链路 = 命令注册 ✓ + UCL accept 规则 ✓ + 加载器白名单 ✓ +
id→name 匹配 ✓ + **NPC 事件路由挂 characters/give ✓**。最后一环才是「没反应」的真正原因。
**上线只需重启一次**（本次改 `events.ex` 一处），重新从 UCL 生成 NPC 进程即生效。
注：玩家须确实持有「捕兽夹」（别名 bushou jia / jia / bushou，item `clone_lib:items.bushoujia`）
且身处猎人所在房间（hengyang:shulin1），否则会看到「你身上没有这样东西」/「这里没有这个人」。
