## 续做 50：清掉 bcrypt NIF（26 条）+ ecto preload（2 条），确定性失败基线 28 → 1

### 背景

上一轮把「27 条 bcrypt 失败」记成「环境限制、不可修」。本批复核后**推翻该结论**。

### 一、bcrypt NIF：不是「没有 C 编译器」，是两处环境叠加

- PATH 上确实没有 `cl/gcc/nmake`，但 `vswhere.exe` 在。
  `vswhere -all -products * -requires Microsoft.VisualStudio.Component.VC.Tools.x86.x64`
  → `2022\BuildTools`（MSVC **14.44.35207**）+ `18\Community`；Windows SDK **10.0.26100.0** UCRT 头/库齐全。
- 真正拦路虎：
  1. `vcvars64.bat` 内部调 `reg.exe`，被本机安全策略拦截 → SDK 的 `INCLUDE/LIB` 未注入 →
     `bcrypt_nif.c(52): fatal error C1083: 无法打开包括文件: "stdio.h"`。
  2. elixir_make 0.6.2 走 `nmake /F Makefile.win`，nmake 横幅是 CP936 中文字节，
     Elixir 1.20 `System.cmd` 按 UTF-8 解码崩：`ArgumentError` → `System.do_port_byte/3`
     → `elixir_make compile.make.ex:223`。`VSLANG=1033`、`chcp 65001` 均无效。
- 解法：绕开 vcvars + 绕开 elixir_make，cmd 里手工设 `PATH/INCLUDE/LIB/ERTS_INCLUDE_PATH` 后直接 nmake，
  产物 `deps/bcrypt_elixir/priv/bcrypt_nif.dll` 再发布到 `_build/{dev,test}/lib/bcrypt_elixir/priv/`
  （`:code.priv_dir/1` 指向 `_build`）。
- 固化为 `scripts/build_bcrypt_nif.bat`（全 ASCII + CRLF，见下「脚本坑」）。
  `deps/`、`_build/` 均 gitignore，产物不入库，换机器需重跑。

### 二、bcrypt 修好后暴露的真 bug：`Zones.get/1` / `Rooms.get/1` 必崩

- 4 条 `ZoneControllerTest` 原先全挂在 `Bcrypt.Base.gensalt_nif/3`（`create_admin` 哈希密码）；
  bcrypt 一好，2 条推进到：
  `UndefinedFunctionError: Ecto.Adapters.Postgres.checked_out?/1 is undefined ... behaviour Ecto.Adapter expects it`。
- 根因是**依赖版本不兼容**：
  - `deps/ecto` **3.6.2** 在 `lib/ecto/adapter.ex:66` 声明非 optional 的 `@callback checked_out?(adapter_meta)`，
    并在 `lib/ecto/repo/preloader.ex:124` 的 `maybe_pmap/3` 里调用——**仅当顶层 preload 条目 ≥ 2**。
  - `deps/ecto_sql` **3.6.1** 全库无 `checked_out`（`grep -rn checked_out deps/ecto_sql/` 零命中）；
    该实现是 **ecto_sql 3.6.2** 才加的（`lib/ecto/adapters/sql.ex:645`）。
    即 ecto 3.6.2 + ecto_sql 3.6.1 是「可解析但不兼容」的组合。
  - `Zones.get/1` 的 `Repo.preload([:staged_changes, rooms: [:staged_changes]])` 正好 2 条 → 必踩；
    `Rooms.get/1` 同理。
- **为什么没直接升 ecto_sql**：
  - `mix deps.update ecto_sql` 会把 ecto 拖到 3.14 / decimal 3.0（major）/ postgrex 0.22，不可控；
  - 只钉 `ecto_sql 3.6.2` 也不行——`deps/ecto` 3.6.2 的 `lib/ecto/query.ex:428` 有
    `@opaque dynamic :: %DynamicExpr{}`，与 Elixir 1.20 新增内建类型 `dynamic/0` 冲突，
    编译期 `Kernel.TypespecError: type dynamic/0 is a built-in type and it cannot be redefined`。
    即本机 `_build` 是**旧 Elixir 编译的缓存**，ecto 在当前工具链下**无法重新编译**。
- 采用**应用层规避**：拆成两次单条 preload，走 `maybe_pmap/3` 串行分支，不触达 `checked_out?/1`：
  - `lib/ex_venture/zones.ex`：`Repo.preload(:staged_changes) |> Repo.preload(rooms: [:staged_changes])`
  - `lib/ex_venture/rooms.ex`：`Repo.preload(:staged_changes) |> Repo.preload(zone: [:staged_changes])`
  - 两处均加注释说明成因 + 「ecto_sql >= 3.6.2 后可合并回一条」。
  - **`in_parallel: false` 无效**：条件为
    `match?([_,_|_], preloaders) and not checked_out?(repo_name) and Keyword.get(opts, :in_parallel, true)`，
    `checked_out?` 排在 `in_parallel` 之前，短路不到。

### 三、构建缓存抢救（重要，别再踩）

`mix deps.update` 一旦动 ecto，`_build/test/lib/ecto` 会被清空并尝试重编译 → 失败 → ebin 归零。
`_build/dev` 未受影响，是干净的同版本产物，可用来还原：

1. `git checkout -- mix.lock`；`mix deps.get` 把 `deps/ecto_sql` 退回 3.6.1；
2. `rm -rf _build/test/lib/{ecto,ecto_sql}`，从 `_build/dev/lib/{ecto,ecto_sql}` 整目录拷回（含 `.mix/compile.elixir`）；
3. **补写 `_build/test/lib/ecto/.mix/compile.elixir_scm`**：`Mix.Dep.Loader.validate_manifest/1` 在
   manifest 缺失且 SCM 可 fetch 时把 dep 标成 `:compile`（`loader.ex:431-432`），于是又去重编译 ecto。
   格式（`Mix.Dep.ElixirSCM`）：`{2, {System.version(), :erlang.system_info(:otp_release)}, Hex.SCM, lock}`，
   `lock` 取 `mix.lock` 里该 dep 的元组；
4. `mix deps` 仍会打印「the dependency build is outdated」，但 `mix test` 已能跑——该提示是历史遗留
   （19 个 dep 都没有/对不上 manifest），**不影响运行，不要去「修」它**。

### 四、脚本两个坑

- 批处理里的**中文注释会被 cmd 当命令执行**（UTF-8 多字节被按 CP936 切分，`rem` 行被截断）→ 脚本全 ASCII。
- 必须 **CRLF** 行尾；LF + 括号块（`for ... ( ... )`）会在词中断行，报 `'riv' 不是内部或外部命令`。
- `_build/test/lib/bcrypt_elixir/priv` 是指向 `deps/bcrypt_elixir/priv` 的**目录联接**：
  `cp` 报 "are the same file"，`copy /Y` 报 "being used by another process"，
  而 `del` 会**连 deps 里的真文件一起删掉**。脚本只做 copy，并以「copy 后文件是否存在」判定成功，绝不 del。
